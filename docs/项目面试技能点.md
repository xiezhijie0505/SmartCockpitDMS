## 1. 采集进程退出标志：`std::atomic_bool` + 信号

**项目位置：** `apps/dms_capture/main.cpp`（S4.2 `dms_capture`）

**场景：**  
`SIGINT`（Ctrl+C）/ `SIGTERM` 的处理函数里把 `g_running` 置 `false`，主循环 `while (g_running.load())` 判断后退出，再 `close` 摄像头、`munmap`。

### 口述（短版）

信号处理函数会异步修改 `g_running`，主循环同时在读。这在 C++ 里是数据竞争，普通 `bool` 是未定义行为——编译器可能把标志优化进寄存器，信号改了内存循环仍停不下来。`std::atomic_bool` 保证读写原子、禁止错误优化，并且写对读可见。信号处理器里不能随便加锁，所以退出开关用 atomic 是常规做法。

### 追问备答

| 追问 | 答法 |
|------|------|
| atomic 能避免同时访问吗？ | 不能。信号仍可能插进来；atomic 保证并发时读到完整正确的值，不是禁止并发。 |
| 为啥信号处理函数不能加锁？若能加锁怎么解决读改冲突？ | 见下方展开。 |
| 帧 shm 里的 `seq` 是啥？和 atomic 退出标志啥关系？ | 见下方展开。 |

#### 追问展开：信号里为啥不能 mutex？能加锁又会怎样？

信号不是新线程，而是**打断当前线程**、插入 `onSignal`，完了再回到断点。

若主循环已经 `mutex.lock()` 还没 `unlock`，此时来了 SIGINT，`onSignal` 里再 `mutex.lock()`：锁规则要求等持有者释放，而持有者正是被打断的主循环——它必须先跑完 `onSignal` 才能回到后面去 `unlock`。于是 onSignal 等 unlock，主循环又卡在 onSignal → **自己等自己 → 死锁**。

若（假设）信号里能安全用锁：靠互斥让「读标志」和「写标志」不同时进入临界区，从「禁止同时访问」保证正确。但信号场景用不了这套，所以退出标志用 `atomic`，不靠锁。

#### 追问展开：`seq` 是什么？

`seq` 是共享内存帧头里的 **序号（sequence）**，用来做 **seqlock（序号锁）**，不是“内存序 seq_cst”的缩写。

- **偶数**：这一帧数据完整，读者可以信  
- **奇数**：写者正在改 `data[]`，读者不要用  

写端（`dms_capture`）：`seq` 先变成奇数 → 写像素/宽高 → **最后**再变成偶数（发布）。  
读端：读 `seq1` → 拷贝 → 再读 `seq2`；若不一致或变成奇数，说明拷的时候被改写了，丢弃重试。

和退出用的 `atomic_bool` 同类点：都是**无锁、一写多读**；差别是 `g_running` 只是开关，`seq` 保护的是「一整帧图像有没有撕开」。

### 一句话

异步信号改标志、主循环读标志 → 必须用 `atomic`；正确且符合信号上下文不能加锁的约束。
